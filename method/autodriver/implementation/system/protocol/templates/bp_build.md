本次任务：为给定的设备行为选择目标操作系统的实现机制，输出一份“目标实现对应方案”。

你会收到三类主要输入：
1. 设备行为模型，简称 DBC。它说明当前策略下必须保持的初始化、设备操作、时间、数据、采集和失败行为。
2. 目标框架接口说明，简称 FP。它说明目标操作系统实际提供哪些调用、事件、资源、时间和输出能力，以及这些能力的前提与限制。
3. 公开集成要求和本次任务要求。它们说明目标入口、注册、容量、范围、数值精度和允许修改的位置等。

目标实现对应方案简称 BP（Binding Plan）。它回答“设备模型中的每个要求怎样用目标能力实现”，不重新选择设备策略，也不修改前两份输入。它不是目标代码的逐行设计。

请为整个设备模型建立对应，并回答：
- 每个设备动作由哪个原生调用执行，参数和长度从设备模型哪里取得。
- 哪个目标事件能够观察本轮设备操作完成；两者是先后关系还是确实相等，依据是什么。
- 等待怎样实现物理下界，以及适用的上界；计数器频率、相位、最小间隔、饱和和回绕有什么影响。
- 缓冲区何时交出、归还、最后使用和重用；帧校验及保存是否已经结束。
- 原生请求何时接受、如何关联一次设备采集、何时成功或失败结束。
- 物理量怎样映射到原生类型、单位、比例、舍入与允许误差，是否有溢出。
- 初始化、并发或恢复要求依赖哪些目标能力，尚有哪些无法建立的前提。

所有设备命令、布局和公式都引用 DBC；框架保证引用 FP。不要复制另一套独立事实。不能把“存在回调”当成物理完成证明，也不能把一个名为“已检查下界”的节点当成证明本身。目标接口无法表达所需错误时报告缺口，不用零或旧样本代替失败。

输出一个 BindingPlan 表达式。device_contract、framework_profile、target_support 用 Ref 引用实际输入材料 ID；动作、事件、数据、资源、请求、数值和并发对应填入其定义字段；保留待检查义务和所有相关父缺口。完整语法和原语含义直接附在本消息后面。将表达式字符串放入响应模板的 artifact.content，并填写证据；不能满足时请求相应资料或上游修订。
