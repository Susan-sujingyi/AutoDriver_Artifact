本次任务：根据给定内部诊断，修订一个指定对象。

输入会直接说明应交付哪种对象；candidate 是它的当前内容，internal_diagnostic 是当前方法内部检查发现的问题。其它输入为原始依据或只读父要求。诊断指出的代码位置可能只是错误表现，不一定是根因。

先核对诊断及其支持的范围，再做当前对象内有依据的修订：
- 若对象为框架接口说明（FP），根据原始接口/文档/实现修订保证与限制；只产生新候选，不发布共享库。
- 若对象为设备行为模型（DBC），在已定策略下修订一份全局模型，检查修改对初始化、采集、失败、数据及恢复路径的影响。
- 若对象为目标实现对应方案（BP），保持设备模型和目标接口说明不变，修订它们之间的对应及义务。
- 若对象为代码，保持所有父要求，遵守编辑范围和完整文件基线。

代码基线明确不存在的文件应依据只读契约和公开 ABI 使用 create 新建，base_sha256=null；内部类型、函数和状态组织由你设计，不需要一份现成目标驱动。不得请求同器件的目标参考实现。上一份响应是无效文本或仅请求资料时，它不是已接受代码，也不妨碍生成针对原始 baseline 的完整累计 file_edits。工具只通过 context_requests 使用：scope=internal_tools，query 为含 tool、arguments 的 JSON 字符串；不能在响应外输出工具参数。

代码修复默认依赖完整当前父对象、公开集成、完整候选和内部诊断。框架原文仍可通过列出的有限工具从同一获准池按需查询，不把未提供的祖先全文当作当前引用。

若根因在本次不能修改的父对象，填写 context_requests，说明哪个事实或要求需要上游核对。本次不要同时改多个层次，不靠删检查、降低要求、换策略或把旧样本当新成功来消除诊断。

修订 DBC 时，独立保留有原文依据的产品要求与器件约束。框架保证未知不意味着要求未知；数值时间上界用带本次事件锚点的 Deadline 表达，不能只保留自然语言。源延时、缓存和返回习惯也不自动成为保持义务；对照冻结配置与器件适用条件，保留明确冲突及其影响。

输出模板已经填好当前对象类型。契约对象在提供 contract_repair_base 时优先用 constructor_edits，只修改必要字段；否则用当前 schema 指定的完整 content。代码对象在 artifact.edits 填累计候选文件修改。所有相关格式定义直接附在本消息中。填写修改依据、仍未解决的问题和简短摘要；证据不足则请求补充，本次无法继续则明确说明。后续是否通过检查由主机决定。
