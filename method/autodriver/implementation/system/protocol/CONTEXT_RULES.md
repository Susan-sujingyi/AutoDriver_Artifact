# 上下文装配规则

## 1. 可信边界与条件

装配器只读已准备的 agent 可见根目录与可信主机登记。登记、预算、实验控制、完整来源链和审计留在主机；模型只收到当前控制投影、必要材料片段、响应 schema 和获准工具名。正式环境仍需独立沙箱与工具网关，不能靠 prompt 实现文件系统隔离。

| 条件 | 允许的器件资料 | 关键排除 |
| --- | --- | --- |
| S | 获准冻结源驱动/配置及必要产品条件 | 原始器件手册及其派生摘要 |
| D | 冻结原始器件资料及必要产品条件 | 源驱动、源配置、源分析、源 FP 及其派生信息 |
| SD | 上述两类 | 仍排除隐藏材料及未批准补充 |
| FRAMEWORK | 与任务无关的获准框架证据 | 仅供 FP 调用，不允许混入器件语义 |

所有条件均禁止：隐藏参考、评分器/评分反馈、真机诊断、校准经验、供应商补充 DOC/DOCX、其他 trial、人工研究实例。批准的公开目标支持不得含针对当前器件的解答实现。通用方法格式说明可以输入；手工核对的 SHT3x DBC/FP/BP 不能借“格式示例”进入正式 prompt。

`approved`、`kind`、`os_role` 以及来源关系必须由可信准备器确定。装配器不能识别被错误标记为“公开支持”的隐藏答案，也不能证明一份人工摘要未混入记忆；这属于准备流程的审计责任。正式实验仍须核对项目冻结 receipt，不在在线阶段重建源输入。

## 2. 按问题检索，再装配

1. 读取原生 task.yaml，准备公开任务字段、产品条件和策略，保留冻结材料身份。不要把整个任务文件、评测路径或完整主机 request 原样发送给模型。
2. 由阶段的 required/optional roles 限定候选材料。按“待恢复语义 → 对应符号/章节/父条目”选择相关证据；先取声明与调用点，保证不足再追 provider 和必要依赖。此检索策略是设计规则，本包没有实现自动检索器。
3. 对每一项所选材料递归检查全部 `parents`。所有祖先必须获准、类型合法、满足当前 S/D/SD 条件且 hash 一致；循环或缺失来源拒绝。派生摘要不能绕过禁用资料，来源链失败时整项材料不能进入 prompt。
4. 检查所选 role 与材料类型、阶段、source/target 角色一致；检查必需角色齐全。源 FP 摘要按需提供，不先装载整个 OS 知识库。共享 FP 必须框架证据闭合，任务内补充不覆盖共享版本。
5. 按 request 中主机确定的顺序装配文本片段，附材料 ID、hash、虚拟路径、原文区间和定位。顺序建议为格式说明、任务、父契约、当前候选、原始证据、内部诊断。相同输入得到相同消息与 hash。
6. 渲染公共输入说明 + 面向模型的阶段任务 + 自动附带的语言说明 + 结构化 user 数据，并检查总预算。先解释目标和术语，再给格式参考。每次附带 response-protocol 和 shared-language；FP 产物/父对象附 fp-language；DBC 附 dbc-language 和用于解释框架效应的 FP 语言；BP 附全部三类语言。代码生成读取三类父契约，亦附全部定义。通用定义属于系统指令，不是可遗漏的任务证据；其 hash 单独审计。审计写入主机独立目录，不能重新当上下文加入模型。

来源闭包的祖先仅用于批准和校验，**不自动全文加入 prompt**。例如 BP 消费 DBC 时检查其来源合法，但只有需要核查的原文才单独选入允许角色。这样既维持边界，也避免把所有派生链展开成冗长上下文。

## 3. 片段完整性与预算

代码证据应覆盖相关定义、有效配置分支、调用者及必要的实现语义；时序和公式证据须覆盖单位、条件、脚注及交叉引用。源 API 声明不能替代其物理完成保证。片段太小导致事实缺口时，模型应请求补充，不能凭名字补齐。

本原型只检查行区间有效，不证明片段语义完整。原始 PDF 可保留 hash 作为派生文本祖先，所选上下文采用机械文本提取并保留页码定位。图、表或时序图信息缺失时，应加入经批准的原始页面图像；当前文本装配器会拒绝直接渲染二进制文件，图像适配器待实现。不得用供应商补充说明替代冻结原文。

`max_context_bytes` 限制规范序列化后整份消息的 UTF-8 字节数，包含模板和响应 schema；它不是 token 预算或付费授权。超限直接拒绝，**不截断字符串、不静默删除必需材料**。主机只能重新检索更窄但语义完整的范围、分拆能力问题/调用，或按当前授权调整预算。真实模型接入还需 provider 对应的 token 与输出预算检查。

代码 `replace/delete` 必须有完整当前文件作为基线输入。create 必须由主机依据完整基线清单和应用时文件系统确认不存在。原型对给定 base_files 做一致性检查，不能证明该清单完整。应用候选前仍须再次核对实际文件。

## 4. 工具与补充请求

工具名表示接口类别，不授予任意 shell 或仓库读取权。实际 executor 应只接收能力受限的参数，返回登记过的材料或内部诊断，并保留工具版本和输入来源。模型提出检索请求后，主机重新经过批准、来源和预算检查，生成下一次调用。

| 工具类别 | 预期结果 | 主机检查 |
| --- | --- | --- |
| inspect_symbol / resolve_configuration / slice_device_effects | 符号、有效分支、I/O 与数据依赖事实 | 当前可见源码范围、配置身份、原文定位 |
| retrieve_device_evidence | 冻结原文的文本/页面/交叉引用 | 当前条件是否允许、机械派生来源 |
| query_framework | 相关 FP 或框架原文 | source/target、版本/配置、能力保证来源 |
| check_contract / check_binding | 方法内部结构、语义或能力诊断 | 检查器确实实现哪些检查、是否独立于评分 |
| read_candidate / compile_candidate / check_candidate | 当前候选或方法内部编译/行为诊断 | 准备副本、可编辑范围、日志内容和来源 |

仅接受 `method_contract_checker`、`method_binding_checker`、`approved_compile_tool`、`method_trace_checker` 产生的内部诊断。真实集成还须移除日志里的主机路径、私有材料和环境值；原型只核对工具身份与声明的来源链。编译诊断可以修复类型/接口问题，编译成功不能充当完整行为正确证据。

FP 调用不能请求设备源码或手册；BP 调用默认只请求目标框架、公开支持或上游阶段。S 不能请求器件资料，D 不能请求源资料或源框架。`context_requests` 的查询字符串只能作为检索文本，不能执行为 shell。`upstream_stage` 仍须遵守原始条件和本次授权。

## 5. 冻结、版本与修复

共享 FP 随 OS 快照与配置版本冻结；在线缺项补入 task-local FP 候选。任务内核验、独立离线审查与新版本发布是不同动作。原型不实现共享库发布。

DBC、BP、代码以 hash 关联父版本，任一父规范发生变化，应重新检查依赖它的下游候选及 generation gate。FP/DBC/BP 修复输出单一新候选，不暗中改代码。代码若暴露上游矛盾，应请求上游重建；不得自行降低器件约束、改变策略或屏蔽未表达错误。

装配审计记录 receipt ID、request/registry/protocol/template/prompt hash、所选材料与来源闭包 hash、实际字节数。模型和真实工具版本、响应 hash、检查器版本及调用成本应由未来网关补充，本包不制造这些记录。主机审计和研究输出不得进入其他调用的证据。

语言目录目前按文件粒度附带全文，预算包含它们。若超过限制，可在未来检索器中按符号依赖闭合选择完整语义条目；本原型不会自动压缩或删减定义。构造器签名从公开语义文档生成机器索引，不独立维护另一份字段表。

每份模型输入还有中文 task_brief（本次目标、交付对象、材料权限）、各材料的 role_description、已填固定标签的 output_template，以及逐项 output_instructions。不要求模型知道 S/D/SD、框架摘要的内部别名或其它对话。response_schema 仍限定真实输出。模型没有实际工具时使用补充请求，不能根据名称虚构调用。prompt_support.py 的 hash 同样进入审计。
